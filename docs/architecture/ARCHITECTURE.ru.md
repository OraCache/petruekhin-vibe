## 1. Назначение и границы

OraCache — распределённый версионный кэш перед основной БД. Принят cache-aside: приложение выполняет Get; после MISS само читает БД и заполняет кэш. Обычный Get не превращается в неявный запрос к БД. Отдельный механизм bulk warmup для холодного запуска нужен конечному решению, но не меняет обычный data path. E-001, E-013.

Для target установлены единый write-region, RF3, версии и необходимость межрегиональной репликации. Single writer задаёт место принятия записей, но не гарантирует свежесть относительно БД. RF3 задаёт число копий, а не готовый sizing или независимость failure domains. Число шардов и их размещение, финальный wire API, поведение при потере primary и SLA не утверждены. E-002, E-003, E-005, E-014.

PoC намеренно уже target: один регион, один статический шард, три storage-процесса, RAM без дисковой persistence; CP и gateway включены. Auto-TTL и разрешение DB/cache гонок не входят в этот PoC. Исторические варианты MVP различаются, поэтому выпуск MVP требует отдельного baseline, а не переименования PoC. E-004, E-015.

## 2. Компоненты и потоки

```text
Приложение ── Get/Put/Delete ──> Gateway ──> Storage node / Raft member
     │                              ↑                  ↔ peers того же шарда
     └── MISS: чтение БД             │ config snapshot
             └── заполнение кэша    CP <── heartbeat / observed state
                                    └── desired configuration
```

- **Gateway** — data-path routing по ключу и снимку конфигурации. CP не вызывается на каждый пользовательский запрос. Ограниченные retry и leader hints не превращают gateway в координатор exactly-once.
- **Storage node** — один процесс с application wiring, транспортом/Raft и store/FSM. Application layer не отдельный промежуточный RPC-сервис. Raft выбирает лидера группы; CP не назначает его heartbeat-ом.
- **Control Plane** — desired/observed state, конфигурация и планирование. Supervisor запускает процессы. Target-правила authority/HA и размещение metadata store ещё требуют решения.
- **Источник данных** — БД приложения. Порядок команд кэша и его revision не задают порядок состояний БД.

Эти роли устойчивы; централизованный либо региональный CP — отдельная развилка. В PoC CP хранит состояние в памяти, storage отправляет heartbeat и отдельно тянет config; ошибки не должны подменять last-known-good пустым снимком. Config revision не равен committed Raft membership. E-009, E-012.

Рабочее межрегиональное направление — региональные группы Raft и асинхронный поток A→B с outbox. Это **предложение протокола**, не реализованная PoC-функция и не подтверждение всех клиентских гарантий. ReadIndex в B ограничен журналом B и не обнаруживает недоставленный хвост A. WAN ACK, RYW, fencing и смена writer относятся к [RFC-003](rfc/RFC-003-recovery.ru.md). E-011.

## 3. Данные, версии и чтения

Продуктовое намерение: Get выбранной/latest версии вместе со списком сохранённых версий; Delete конкретной версии; ограниченная конфигурируемая история. Точное представление списка и трактовка удаления текущей версии не завершены. Кэш выдаёт собственную version, поэтому ранний алгоритм «принимать только более новую DB revision» нельзя применять без отдельного источника порядка БД. Все промежуточные состояния БД не обещаны одной лишь N-историей кэша. E-005, E-008.

Для TTL установлено продление всех версий при чтении ключа. Локальный Get в B с фоновым asyncTouch ослабляет эту гарантию; первичного согласия на замену не установлено. Продлеваемый TTL не ограничивает возраст данных относительно БД у горячего ключа. [RFC-002](rfc/RFC-002-ttl.ru.md) разделяет freshness и liveness. E-007.

В проверенном историческом PoC revision — глобальная последовательность store, retention по умолчанию 3, CAS проверяет последнюю cache revision. Default read проходит через лидера/ReadIndex и ожидание apply; Local допускает устаревание. Hash mapping — xxhash64(key) % partition_count, не consistent hash ring. Это характеристики среза кода, не финальные продуктовые обещания. E-006, E-010.

Два связанных **реальных расхождения** API: GetResponse содержит Data/Rev/LatestRev, но не history list; Delete текущей отдельной версии может открыть предыдущую как latest, а rev=0 удаляет ключ целиком. Таким образом, наличие истории внутри store не означает выполнение контракта Get, а успешный Delete не доказывает ожидаемый MISS после удаления текущей. Исправление кода этим пакетом не производится. E-006.

## 4. Отказы, восстановление и готовность

PoC показывает перевыбор лидера при сохранении работоспособного большинства. Это не recovery после потери памяти. MemoryStorage теряет log/term/vote/snapshot; RAM checkpoint не делает безопасным rejoin прежнего peer ID после рестарта. Snapshot catch-up живого follower не равен восстановлению уничтоженного узла. Warmup schema сама по себе не доказывает runtime warmup. E-013.

Конечному продукту нужен bulk-прогрев, в том числе после потери всех копий шарда. Ручная инициация допустима; механизм должен быть частью решения, а не обязательным самописным циклом приложения. Одна версия для прогрева допустима. Peer catch-up внутри группы, logical resync независимого региона и cold import из БД — три разных процедуры. E-013, E-011.

Для target остаются открыты ACK/RYW, staleness, допустимые потери, RPO/RTO, readiness, backpressure и смена primary. Обсуждение потери региона не является полной приёмкой отказных гарантий. Нельзя обещать запись после потери A, zero-RPO или global linearizability только на основании single writer. E-002, E-011.

## 6. Условия следующего архитектурного решения

Четыре RFC содержат варианты и различающие сценарии, а не скрытые решения. До утверждения MVP необходимо выбрать минимальный клиентский контракт, отказную модель и измеряемую приёмку. Рабочий профиль нагрузки, p95/p99, ресурсный бюджет CP/Gateway, объём истории, lag/readiness и допустимая DB-load требуют конкретных значений; **пороги не установлены**. Оценки из материалов не выдаются за измерения. E-014.
