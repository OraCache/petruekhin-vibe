# RFC-003: межрегиональная репликация, recovery и warmup

**Статус: открыт; региональные отказные гарантии не приняты этим RFC.** Scope: target и baseline MVP. Основания E-002, E-009, E-011, E-013; требования R-015…R-019. Связи: [API](RFC-001-api.ru.md), [топология](RFC-004-topology.ru.md).

## Установленное и рабочее направление

Single write-region и необходимость репликации установлены. Направление команды: региональные Raft-группы, outbox A→B, импорт непрерывного префикса. Предлагаются атомарные state/result(opID)/outbox в A и идентификация потока shard/writerEpoch/sequence; импорт не должен порождать обратный исходящий поток. Это описание предложения, не реализованного PoC WAN-протокола.

Default ACK, допустимые потери при гибели A и смена writer не закрыты. Отсутствие автоматического promotion в рабочем плане не равно принятию заказчиком недоступности записи после отказа региона.

## Варианты ACK и чтений

| Вариант | Что означает success | Компромисс |
|---|---|---|
| PRIMARY_DURABLE | Majority A + apply, с устойчивым состоянием и outbox; B не ждём | Ни zero-RPO при уничтожении A, ни немедленный RYW в B не следуют |
| ALL_REGIONS_DURABLE | Подтверждены оговорённые устойчивые позиции регионов | WAN latency/недоступность B влияет на writes; состав регионов в ACK должен быть определён |
| Position-aware read | Клиент ждёт позицию в B либо читает A | Отдельное усиление RYW, не изменение факта недоставленного хвоста |

Названия durable не применимы к RAM PoC. ReadIndex B подтверждает только локальный журнал B. Численные RPO/RTO, допустимая staleness и timeout ожидания позиции **не установлены**.

## Recovery: три разных механизма

1. **Peer одной группы:** durable log/term/vote/membership/FSM и безопасный snapshot+tail; после потери памяти нельзя автоматически вернуть старый peer ID с чистым MemoryStorage.
2. **Независимая региональная группа:** logical snapshot состояния с позицией входящего потока, затем непрерывный tail. Нельзя просто установить сырой Raft snapshot A в группу B с другой историей.
3. **Потеря всех копий / cold start:** встроенный bulk import из источника. Ручная инициация допустима; одной версии достаточно для warmup. CSV/дамп — примеры, не выбранный формат. Readiness и дополнительная нагрузка БД должны измеряться.

## Альтернативы хранения и управления отказом

- Durable log + state/checkpoint ускоряет восстановление, но требует доказать атомарные границы данных, outbox, dedup и cursor. Конкретный engine не выбран.
- Потеря значений с восстановлением из БД может упростить cache storage, но не разрешает терять версии/fencing/dedup-обязательства, если выбранный API на них опирается. Одного списка горячих ключей недостаточно для durable cache state.
- Ручной promotion с fencing либо автоматизированный координированный failover имеют разные эксплуатационные требования. Ни один не выбран здесь; configVersion, Raft term и writerEpoch не взаимозаменяемы.

## Проверки и условия закрытия

Проверить gap/duplicate/reorder потока, повтор opID на границе snapshot, нехватку памяти B/backlog A, WAN partition, полную потерю A и возвращение старого A после promotion. Проверить потерю большинства, crash между effect/result/outbox, восстановление заменённого peer и cold bulk import без копий кэша. В каждом сценарии определить success/unknown/отказ и возможную потерю; измерить lag, DB-load, readiness и RTO.

PoC killleader проверяет только локальное большинство. Catch-up живого follower не crash-rejoin; warmup proto не runtime. Для закрытия RFC нужны выбранные ACK/RYW/fencing, retention obligations, storage protocol, источник warmup и численные пороги. Владелец/срок не установлены; production-гарантии без этих решений не заявляются.
