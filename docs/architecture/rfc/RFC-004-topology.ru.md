# RFC-004: CP authority, топология и изменения состава

**Статус: открыт; роли установлены, финальная authority не выбрана.** Scope: target и baseline MVP. Основания E-003, E-010, E-012, E-014; требования R-020…R-023. Связь: [recovery](RFC-003-recovery.ru.md).

## Границы решения

CP ведёт конфигурацию и desired/observed state; gateway маршрутизирует data path; Raft выбирает leader; supervisor запускает процессы. Application/store/FSM — слои storage-процесса, не цепочка новых RPC-сервисов. RF3 и одинаковые pod установлены; конкретное число шардов, metadata placement и весь рисунок размещения не приняты целиком.

Два исторических Git-документа различны: distributed-cache-topology описывает роли, mapping, add/drain и каталоги; raft-design — журналы/outbox/persistence и этапы реализации. План второго не заменяет описание топологии первого. Их точные SHA/локаторы сохранены в E-010/E-013.

## Альтернативы CP

| Вариант | Плюсы | Риск / основание выбора |
|---|---|---|
| Authority на master-region с возможным расширением | Проще baseline MVP, единый источник desired config | Доступность управления и stale config при потере A; не объявлять требованием единственного global CP |
| Региональные CP с согласованной authority/обменом каталогами | Локальная операционная автономность | Нужны правила конфликтов/epochs, HA metadata и fencing; наличие каталога не даёт права сменить writer |

## Выбранный следующий шаг PoC: статическая конфигурация и наблюдаемый лидер

Последующее решение владельца: отказаться от leased discovery в ближайшем PoC и сохранить раздачу заранее заданной конфигурации через CP. Предыдущее решение о каталоге discovery остаётся историческим этапом, а не действующим требованием этой модификации. Подробности — [ADR-005](../adr/ADR-005-static-leader-hints.ru.md).

- Конфигурация задаёт регионы, адреса нод и назначения реплик. Состав Raft на storage-нодах пока статический.
- Heartbeat от известной реплики, которая сообщает себя готовым лидером, обновляет подсказку leader_id + term для (region, partition). Меньший term не перезаписывает больший. Противоречие одинакового term не разрешается последним прибывшим сообщением.
- Наблюдения передаются gateway отдельно от ревизии статической конфигурации. Их обновление должно приходить и тогда, когда конфигурация не менялась.
- Gateway пробует наблюдаемого лидера, затем остальные известные реплики, обрабатывает NOT_LEADER. Корректность запроса обеспечивает Raft; heartbeat не доказывает наличие кворума.
- Адреса не регистрируются через heartbeat, leases/TTL каталога не используются. При потере CP остаётся последняя карта и перебор реплик; это не гарантия свежести адресов и не writer fencing.
- CP хранит наблюдения в RAM. Ограничения рестарта и порядок обработки старых ответов должны быть явно проверены, без обещания долговечной replay-защиты.
- Сейчас нет mTLS и проверки подлинности отправителя. Принадлежность ID к конфигурации — проверка объявления, не аутентификация.

Статус этого раздела — выбранный контракт модификации, не утверждение о завершённых тестах. Предыдущий опубликованный implementation snapshot 924c2d79a88ca30b7a6e86ef7b8914470722a6f2 ещё содержит leased discovery.

## Будущие варианты управления

А: peers задаются при запуске каждой реплики. Б: управление назначает шард и выдаёт bootstrap/join-настройки. В: scheduler распределяет реплики по пулу storage-нод. Б удобнее при частых заменах, но не является условием корректности; ближайший PoC сохраняет статические peers варианта А.

Направление для будущего oractl: явная операция node add, локальная генерация приватного ключа и CSR, выдача сертификата, learner/catch-up, подтверждённый membership. Наличие сертификата не означает членство в шарде. Автоматический scheduler позже вызывает те же безопасные операции. CLI, mTLS и динамический join в текущую модификацию не входят.

Для target предпочтение обсуждается в пользу региональных Raft-групп и независимого от каждого WAN-запроса data plane. Карта шардов, observed leader и writer authority разделяются. Централизация/HA управления, fencing и смена write-region остаются открытыми, см. RFC-003. Это предложение архитектуры, не автоматически принятое продуктовое требование.

## Топология и migration

Простая отдельная pod на экземпляр шарда поддержана командой. Несколько peers в процессе требуют отдельного обоснования балансировки и failure domains, но не запрещены абсолютно. PoC mapping xxhash64(key)%partition_count при count=1 не задаёт target vectors и стратегию изменения count.

Предложенная безопасная последовательность add/drain: learner → snapshot/log → достижение контрольной apply-позиции → committed membership → публикация маршрутов → cleanup. Desired peer не считается уже committed; завершение копирования не разрешает удалить donor. Буквальное вечное lag=0 не критерий готовности под непрерывной записью. Нужно определить стабильную контрольную позицию и условия promotion.

Изменение числа реплик и изменение числа шардов/key mapping — разные операции. Online resharding вынесен из базового предложения. Ручной запуск миграции не означает ручной перенос данных вместо механизма. Kubernetes — вариант deployment, а не обязательный вывод из pod-схемы.

## Проверки и закрытие

Проверить недоступность CP при живом data plane, last-known-good, устаревший/переставленный config, конфликты revisions, stale leader hints и исчерпание deadline/retries. Для add/drain прервать каждую фазу, проверить membership, маршруты и невозможность преждевременного cleanup. Отдельно проверить размещение RF3 в независимых failure domains.

Закрытие требует выбранной authority/HA, CP/Application API, topology epochs и stale-config policy, hash vectors/числа шардов/placement, migration state machine. Для sizing нужны реальные нагрузочные измерения CPU/RAM/network/disk **включая CP и gateway**, а не прежние расчётные примеры. SLO/ресурсные и readiness thresholds unspecified; владельцы и сроки не установлены.
