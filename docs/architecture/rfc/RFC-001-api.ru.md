# RFC-001: API, версии, инвалидация и гонки

**Статус: открыт; ни один вариант ниже не выбран этим RFC.** Scope: target и выбор baseline MVP. Основания E-005, E-006, E-008, E-009; требования R-006…R-011. Связи: [TTL](RFC-002-ttl.ru.md), [recovery](RFC-003-recovery.ru.md).

## Установлено и в чём расхождение

Кэш назначает собственную version; нужны latest/explicit Get, ограниченная история и Delete конкретной version. Намерение Get включает список сохранённых версий, но wire-формат не завершён. PoC GetResponse возвращает один Data/Rev/LatestRev без history list. Удаление newest может открыть previous; rev=0 удаляет весь ключ. Это не эквивалент намерению MISS после удаления current.

Ранняя монотонная DB revision, поздняя cache revision, право заполнения lease и идентификатор повторной операции — разные сущности. Отвергнуты обязательный монотонный внешний tie-breaker и строгая сериализация всех обновляющих Put. Это не запрет обсуждать клиентский API. N принятых cache-версий не означает каждое промежуточное состояние БД.

## Развилки контракта

| Вопрос | Варианты | Критерий выбора / цена |
|---|---|---|
| Get history | Один value + metadata/version list в одном ответе; либо отдельный history endpoint | Первый ближе установленному намерению и даёт единый срез; второй требует явного согласования отступления и snapshot token/оговаривания гонки |
| Delete current | Current marker/tombstone → latest MISS, старые доступны явно; либо latest становится previous | Второй соответствует PoC, но требует согласовать семантическое изменение; первый требует lifetime marker и защиты от resurrection |
| Delete без version | Отклонять; либо отдельная явно названная операция удаления ключа | Не смешивать версионный Delete и полную инвалидацию; определить идемпотентный результат absent |
| Update/fill | Invalidate после DB commit; dirty/BeginUpdate-EndUpdate; lock/lease; CAS + reread/invalidate | Выбирать по допустимой staleness, обязательствам клиента, цене ожидания и поведению crash/timeout; CAS сам по себе не даёт свежесть БД |
| Retry | Устойчивый operationID + сохранённый результат; либо явный unknown outcome и reconciliation | Первый требует атомарности effect/result и retention; второй оставляет больше обязанностей клиенту |

Invalidate с сохранением истории отличается от удаления всего ключа. Ранний спорный абзац InvalidateKey не является согласованным решением. При lease надо отдельно выбрать WAIT, stale read или MISS для остальных readers. SWR — возможное ослабление, не текущая гарантия.

## Контрпримеры, которые должен выдержать выбор

1. Читатель получает старую БД до commit другого writer и заполняет кэш после него. Успешный cache CAS не доказывает, что значение свежее.
2. Put применён, ответ потерян, gateway повторяет запрос. Безусловный Put может создать новую rev; условный — конфликт после уже успешного эффекта. Proposal ID не равен устойчивому operationID.
3. DB-транзакция переживает lease/dirty timeout; поздний commit приходит после снятия защиты. Непрерывные writers могут не оставлять окна для безопасного fill.
4. Удалить newest при сохранённой old, получить latest и explicit old; проверить, не произошло неоговорённое resurrection. Повторить после TTL/eviction/restart и потери dedup metadata.
5. После регионального переключения повторить opID, не попавший в доставленный префикс. Региональная копия не знает недоставленный результат.

Внутреннее обсуждение связывает строгую гарантию с доставляемым after-update уведомлением либо before-update при известной верхней границе выполнения. Это условие, не принятое клиентское обязательство и не формальное доказательство алгоритма.

## Открытый контракт повторов gateway

Существующий PoC имеет ограниченные retries и не заявляет exactly-once. Для target нужно явно определить, какие ошибки гарантируют отказ до применения, а какие означают неизвестный результат, и какие повторы разрешены самому gateway для Get, Put и Delete. Один gRPC-код ошибки без оговорённого серверного контракта не доказывает отсутствие эффекта.

Варианты: автоматически повторять только гарантированный отказ до предложения записи; разрешать повторы неоднозначных записей с устойчивым operationID; либо возвращать клиенту unknown outcome с процедурой проверки результата. Выбор не сделан. Требуется согласовать общий deadline, лимит попыток и взаимодействие повторов клиента с повторами gateway. Проверки: применение с потерей ответа, смена лидера перед повтором, истечение caller deadline и повтор условной записи после уже успешного эффекта.

Это уточнение открытого API-вопроса, не утверждение нового требования PoC и не разрешение расширить автоматические повторы в текущем коде. Протоколы смены карты и поколения группы обсуждаются в [RFC-004](RFC-004-topology.ru.md).

## Что требуется для закрытия

Согласовать свежесть, полноту истории, Delete/current и response schema; явно зафиксировать допустимые клиентские изменения и unknown outcomes. Для выбранного варианта описать состояния и атомарные переходы, retention/generation, затем выполнить указанные schedule-тесты и обновить protobuf/контрактные тесты. Численные stale bound, lease timeout и opID retention **не установлены**. Владелец решения и срок не установлены. Закрытие RFC не разрешает автоматически публикацию частных оснований.
