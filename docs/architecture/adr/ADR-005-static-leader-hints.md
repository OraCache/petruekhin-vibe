# ADR-005: эксперимент со статической картой и подсказками о лидере

Статус: экспериментальная реализация; окончательное архитектурное решение не принято. Прежняя формулировка о выбранной архитектуре исправлена по текущему уточнению владельца E-017. ID и путь сохранены для истории и ссылок. Предложения по CP/discovery находятся в [RFC-004](../rfc/RFC-004-topology.md).

Область: [однорегиональный PoC с одной статической Raft-группой](../REQUIREMENTS.md#r-004). Факт реализации и прежних проверок — E-018, [отчёт](../STATIC-LEADER-VERIFICATION.md).

## Контекст

Gateway должен находить участника нужного шарда и переживать смену лидера. Для продолжения интеграции был реализован вариант с заранее заданными адресами и отдельными наблюдениями о лидере. CP предоставляет рабочую основу экспериментов; [окончательная модель управления и service discovery ещё открыта](../REQUIREMENTS.md#r-020).

## Ограниченный предмет записи

Эта запись сохраняет контракт конкретной реализации. Она не утверждает выбор статической карты для MVP или target и не объявляет прежний discovery отклонённой архитектурой. Почему эксперимент был реализован именно так, нельзя целиком восстановить из кода или успешного теста.

## Реализованный вариант

CP загружает регионы, адреса узлов и назначения реплик из статической конфигурации. Storage запускается с заранее заданными Raft peers. Gateway получает карту через GetConfig. Отдельный heartbeat от готовой реплики, сообщающей себя лидером, может обновить пару leader_id/term для региона и partition — идентификатора шарда в этом API. Адрес берётся из карты.

Term — номер раунда Raft-выборов внутри истории группы. CP сохраняет порядок наблюдений по term; меньший term не заменяет больший, а разные лидеры при одинаковом term образуют конфликт. Наблюдения доставляются при неизменной ревизии карты. Gateway сохраняет наибольший известный term и не понижает его из-за пустого ответа CP после рестарта.

При неизменной подсказке и той же цели маршрута gateway сначала пробует последний успешный адрес этого шарда в нужном регионе. Без такого предпочтения он пробует наблюдаемого лидера (если пригодной подсказки нет — назначенного картой), затем остальные настроенные реплики. Смена наблюдения или цели маршрута лишает старое предпочтение силы. Перед каждой попыткой адрес сверяется с текущим назначением.

Для Get, Put и Delete отказ `NOT_LEADER` до передачи команды в Raft допускает повтор; адрес из ответа используется только для назначенной реплики. При `Unavailable` gateway может повторить любую из трёх операций. Для записи это неоднозначный исход: потеря ответа не означает, что Put или Delete не применился. При `DeadlineExceeded` отдельной попытки можно повторить Get, но не Put или Delete. Все повторы ограничены числом попыток и общим сроком запроса. При недоступности CP известные маршруты сохраняются. Heartbeat не добавляет реплику в Raft-группу и не меняет её membership — состав участников.

## Следствия и ограничения эксперимента

Статический список ограничивает множество адресов, используемых gateway, но сам по себе не аутентифицирует отправителя heartbeat. TLS и аутентификация в PoC не добавлены. Подсказка может устареть сразу после получения; действующее право обслужить операцию проверяет storage/Raft.

Наблюдения CP хранятся в RAM. Защита gateway от меньших term живёт до его рестарта; общей долговечной защиты от повторной доставки старых сообщений нет. Для пересоздания группы с тем же идентификатором нужен отдельно выбранный протокол поколения группы. Смена карты, динамический join, scheduler и writer fencing не реализуются этим вариантом.

Прежний каталог адресов с leases ограничивал время использования маршрута без свежих наблюдений. Статический вариант сохраняет маршруты при потере CP, но не устанавливает их свежесть после изменения размещения. Это сравнение двух экспериментальных режимов, не утверждённый итог выбора discovery.
