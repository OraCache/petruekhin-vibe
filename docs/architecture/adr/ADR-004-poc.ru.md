# ADR-004: рамка интеграционного PoC

**Статус:** подтверждённая владельцем рамка PoC; дата отдельного scope-подтверждения в источнике не установлена. Не согласование production заказчиком. Основание E-004, E-013, E-015, E-016; требования R-004, R-014, R-019, R-024.

## Решение и назначение

Один регион, один статический шард, три storage-процесса, CP + gateway, RAM без дисковой persistence. Минимально соединить существующие компоненты, проверить data path и перевыбор лидера. План 05.11 исключает auto-TTL и окончательное решение гонок.

Application layer соединяет store/Raft/транспорты/gRPC/CP-agent/lifecycle внутри storage-процесса; это не новый сетевой сервис. Реплицируемый adapter читает через Peek для детерминизма; LRU в этом пути write-driven.

## Альтернатива и последствия

Полный двухрегиональный durable MVP потребовал бы WAN-протокола, recovery, готового API и приёмки, не необходимых для узкой проверки интеграции. Уменьшение PoC экономит объём реализации, но не отменяет target-требования.

RAM checkpoint не доказывает safe restart/rejoin прежнего peer после потери памяти. Успешный CAS не доказывает актуальность БД, а retries без устойчивого operationID — exactly-once. API имеет известные расхождения Get history list и Delete newest→previous.

PoC не принимается этим ADR как MVP/target. Контрактные и отказные вопросы находятся в четырёх RFC.

## Текущее уточнение

Для следующей модификации выбран более простой вариант: статическая конфигурация CP и подсказки о лидере из heartbeat, без каталога адресов с leases. См. [ADR-005](ADR-005-static-leader-hints.ru.md) и [RFC-004](../rfc/RFC-004-topology.ru.md). Модификация локально реализована и проверена: [результаты](../STATIC-LEADER-VERIFICATION.ru.md). Код опубликован отдельными CP/gateway/application ревью; зафиксированные CI-результаты приведены в отчёте проверки. Исторические проверки выше не доказывают работоспособность нового режима.

## Историческое дополнение: discovery через heartbeat с TTL (заменено ADR-005)

**Статус: согласовано владельцем как следующий шаг развития PoC; ещё не утверждение реализации.** Это новое уточнение после исходного reviewed-source-snapshot, не историческое решение заказчика.

**Граница применимости:** решение относится к PoC. Production-архитектура может отличаться; ни статическая конфигурация Raft-групп, ни конкретная схема discovery/CP не становятся production-требованиями автоматически. Перенос в production требует отдельного решения с учётом эксплуатационных и отказных требований.

- Состав Raft-групп и адрес CP задаются статически на storage-нодах. Постоянный master не назначается конфигом: текущего лидера выбирает Raft.
- Storage-ноды сообщают CP свои адреса, принадлежность к группам и текущее состояние через heartbeat.
- CP строит динамический каталог и снимок маршрутизации из этих сообщений; отдельный статический список storage-нод в CP/gateway не требуется. Gateway получает каталог от CP.
- Наблюдения имеют TTL: отсутствие свежего heartbeat делает запись устаревшей. TTL discovery не является TTL данных кеша.
- Heartbeat не изменяет Raft membership и не выбирает лидера. Gateway сохраняет NOT_LEADER/leader hints и ограниченный retry как защиту от устаревшего снимка.

Политики протухания и проверки описаны в [RFC-004](../rfc/RFC-004-topology.ru.md). Численные интервалы, формат сообщений и поведение при потере CP ещё не выбраны. Код и runtime-проверки этим дополнением не изменены.
