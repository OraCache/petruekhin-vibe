# ADR-004: рамка интеграционного PoC

Статус: рамка эксперимента подтверждена владельцем. Точная дата исходного scope-подтверждения не установлена; текущие границы уточнены в E-017. Это решение об объёме PoC. Основания E-004, E-013, E-015, E-016.

## Контекст

Store, Raft, transport, CP и gateway разрабатывались как отдельные части. Узкий интеграционный эксперимент нужен, чтобы проверить совместный путь запроса и смену лидера, не дожидаясь готовности полного межрегионального продукта. Исторические планы MVP различаются, поэтому [объём этого эксперимента нельзя использовать как состав первого выпуска](../REQUIREMENTS.md#r-005).

## Решение

Ограничить интеграционный PoC [одним регионом, одним статическим шардом, тремя storage-процессами, CP и gateway](../REQUIREMENTS.md#r-004). Данные и состояние Raft остаются в памяти, peers задаются статически. План 05.11 [исключает auto-TTL](../REQUIREMENTS.md#r-014) и окончательное решение гонок.

Слой application собирает store, Raft, gRPC, transport, CP-agent и lifecycle внутри storage-процесса. Его задача — соединить библиотеки; дополнительный сетевой сервис между Raft и store для этой интеграции не требуется.

## Основания и последствия

Рамка позволяет отдельно проверить интеграцию существующих частей и локальный отказ лидера. Двухрегиональная репликация, дисковое восстановление и завершённый API потребовали бы других решений и испытаний. Это объясняет предел полезности эксперимента, но не отменяет требований target.

[Потерявший память peer нельзя безопасно возвращать в выжившую группу под прежним ID](../REQUIREMENTS.md#r-019). Контрольная копия состояния в RAM не снимает это ограничение. В историческом срезе `f49c2502d0dda53b56d0cadfa321312122e00095` адаптер читает через Peek для детерминированного порядка вытеснения, который меняют записи. В том же срезе остаются расхождения Get history list и Delete текущей версии. E-006, E-013, E-015.

## Что проверено

Сохранённый запуск `f49c2502d0dda53b56d0cadfa321312122e00095` [показал node-2 → node-3 с операциями через прежний gateway](../REQUIREMENTS.md#r-024). Отдельный fork CI `7a66211c961b05d0de4773e1b67802a81d0f0c05`, run 43604228862: test/e2e/poc success. Эти свидетельства не объединяются в один запуск. Более поздние проверки статического CP описаны в [отчёте](../STATIC-LEADER-VERIFICATION.md). В этой редакции runtime-тесты не повторялись.

## Исправление статуса CP/discovery

Прежняя редакция включала дополнение о heartbeat discovery с TTL как согласованное решение, а последующий ADR-005 — как его замену. Текущее уточнение владельца ограничивает смысл этих материалов: CP сделан временной рабочей основой; окончательные CP и service discovery не утверждены. Исправляется документная фиксация согласования. Оснований описывать это как отмену принятой целевой архитектуры нет. E-017.

Исторические реализации сохраняют значение as-built: сначала каталог с leases, затем статическая конфигурация с подсказками о лидере. Их существование и проверки не выбирают финальный вариант. [ADR-005](ADR-005-static-leader-hints.md) описывает экспериментальную базу; [RFC-004](../rfc/RFC-004-topology.md) содержит открытый выбор. Рамка PoC остаётся подтверждённой.

## Чтение напрямую с узла

Отдельно от интеграционного стенда, срез standalone storage `842cca19950c6aba5a9ced467ca9d1a5fd641213` позволяет обращаться прямо к узлу без CP и gateway. Режим задаётся [при запуске процесса](https://github.com/OraCache/OraCache/blob/842cca19950c6aba5a9ced467ca9d1a5fd641213/cmd/storage-node/main.go): `--read-mode=linearizable` по умолчанию требует лидера, `local` разрешает чтение уже применённого состояния follower, которое может отставать. [TestStandaloneStorageCluster](https://github.com/OraCache/OraCache/blob/842cca19950c6aba5a9ced467ca9d1a5fd641213/internal/node/storage_cluster_test.go) описывает оба режима на трёх узлах в одном процессе с настоящими HTTP и gRPC. Это другой путь запроса, не Compose smoke через gateway.
