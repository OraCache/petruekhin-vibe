## Что реализовано

Статические адреса и назначения загружаются через --config. Лидерские heartbeat обновляют отдельные term-ordered подсказки; GetConfig доставляет их и при неизменной config revision. Конфликт разных лидеров в одинаковом term остаётся конфликтом до большего term. Gateway не откатывает известный term из-за пустых наблюдений после перезапуска CP.

При неизменной подсказке и той же цели маршрута gateway сначала пробует последний успешный адрес этого шарда в нужном регионе. Без такого предпочтения он пробует наблюдаемого лидера (если пригодной подсказки нет — назначенного картой), затем остальные настроенные реплики. Смена наблюдения или цели маршрута лишает старое предпочтение силы. Перед каждой попыткой адрес сверяется с текущим назначением.

Для Get, Put и Delete отказ `NOT_LEADER` до передачи команды в Raft допускает повтор; адрес из ответа используется только для назначенной реплики. При `Unavailable` gateway может повторить любую из трёх операций. Для записи это неоднозначный исход: потеря ответа не означает, что Put или Delete не применился. При `DeadlineExceeded` отдельной попытки можно повторить Get, но не Put или Delete. Все повторы ограничены числом попыток и общим сроком запроса. Изменившаяся подсказка CP вытесняет старое предпочтение; неизменная подсказка не стирает адрес, успешно найденный по запросам. Запоздавший результат старого запроса не затирает предпочтение, выученное при новой подсказке.

Leased discovery, динамическая регистрация адресов, discovery-region/group и локальное истечение адресов исключены. Состав группы не меняется автоматически. [При потере CP остаются известные маршруты](REQUIREMENTS.md#r-020).

В более позднем интеграционном срезе `70c07350dc473b171945f40794e21fb4522dcf2e` порядок адресов и политика повторов сверены по [Forwarder](https://github.com/OraCache/petruekhin-vibe/blob/70c07350dc473b171945f40794e21fb4522dcf2e/internal/gateway/forwarder.go). Это проверка кода, не повтор перечисленных ниже запусков.

## Чего это не доказывает

Нет WAN-приёмки, durable recovery, безопасного rejoin потерявшего RAM peer, mTLS, динамического membership, scheduler, writer fencing, exactly-once или нагрузочных SLO. Подсказка о лидере не удостоверяет кворум и не является разрешением записи.

## Чтение напрямую с узла

Отдельно от интеграционного стенда, срез standalone storage `842cca19950c6aba5a9ced467ca9d1a5fd641213` позволяет обращаться прямо к узлу без CP и gateway. Режим задаётся [при запуске процесса](https://github.com/OraCache/OraCache/blob/842cca19950c6aba5a9ced467ca9d1a5fd641213/cmd/storage-node/main.go): `--read-mode=linearizable` по умолчанию требует лидера, `local` разрешает чтение уже применённого состояния follower, которое может отставать. [TestStandaloneStorageCluster](https://github.com/OraCache/OraCache/blob/842cca19950c6aba5a9ced467ca9d1a5fd641213/internal/node/storage_cluster_test.go) описывает оба режима на трёх узлах в одном процессе с настоящими HTTP и gRPC. Это другой путь запроса, не Compose smoke через gateway.
