# Статический PoC: историческая инженерная запись

Статус: архивная запись экспериментальной реализации. Прежняя формулировка «принято» не подтверждает [окончательный выбор CP или discovery](REQUIREMENTS.md#r-020); статус исправлен по E-017. Актуальное объяснение и точные границы — [ADR-005](adr/ADR-005-static-leader-hints.md), варианты — [RFC-004](rfc/RFC-004-topology.md).

Ниже сохранены инженерные детали для сопоставления с кодом и тестами, не предписание target. Результаты запусков и SHA находятся в [отчёте](STATIC-LEADER-VERIFICATION.md). E-018.

## Контракт реализованного эксперимента

В этом срезе CP служит источником статической конфигурации: регионы, ноды, клиентские адреса и назначения partition на реплики. Storage-процессы запускаются с заранее заданными Raft peers. Gateway получает конфигурацию через существующий GetConfig. CP не находится на пути каждого запроса к данным.

Heartbeat не регистрирует новые адреса и не меняет membership. Он сообщает наблюдаемого лидера. CP принимает подсказку только от известной реплики соответствующей региональной группы, которая сообщает готовность, роль LEADER, собственный node_id как leader_id и ненулевой term. Адрес берётся из конфигурации, не из heartbeat. Аутентификации и TLS в PoC нет; проверка конфигурации не доказывает подлинность отправителя.

Подсказка идентифицируется парой (region, partition_id) и содержит leader_id и term. Задержанное сообщение с меньшим term не заменяет более новое. Противоречивые сообщения разных лидеров с одинаковым term не разрешаются по принципу «кто пришёл последним».

Желаемая конфигурация и наблюдения о лидерах имеют разные жизненные циклы. Heartbeat не должен увеличивать ревизию статического конфигурационного файла. GetConfig должен доставлять обновлённые подсказки даже при неизменной ревизии конфигурации. Gateway не откатывает известный term из-за старого ответа или отсутствия наблюдений после перезапуска CP.

При неизменной подсказке и той же цели маршрута gateway сначала пробует последний успешный адрес этого шарда в нужном регионе. Без такого предпочтения он пробует наблюдаемого лидера (если пригодной подсказки нет — назначенного картой), затем остальные настроенные реплики. Смена наблюдения или цели маршрута лишает старое предпочтение силы. Перед каждой попыткой адрес сверяется с текущим назначением.

Для Get, Put и Delete отказ `NOT_LEADER` до передачи команды в Raft допускает повтор; адрес из ответа используется только для назначенной реплики. При `Unavailable` gateway может повторить любую из трёх операций. Для записи это неоднозначный исход: потеря ответа не означает, что Put или Delete не применился. При `DeadlineExceeded` отдельной попытки можно повторить Get, но не Put или Delete. Все повторы ограничены числом попыток и общим сроком запроса. Подсказки не являются доказательством действующего кворума; право обслуживать linearizable-запрос проверяет storage/Raft.

## Отличие от прежнего discovery

В этом варианте отсутствуют динамическая регистрация адресов, discovery-region/group, каталог с leases и fail-closed после истечения heartbeat TTL. При недоступном CP gateway продолжает обращаться к известным репликам по последней конфигурации. Это не обещание бесконечной свежести: при изменении размещения нужен отдельный протокол обновления конфигурации.

Подсказка о лидере может устареть сразу после получения. Истечение времени без heartbeat не меняет membership и не даёт права выбирать нового writer-региона.

## Границы

- Один регион и одна статическая Raft-группа в проверяемом PoC; интерфейс наблюдений различает регионы и partition.
- CP хранит наблюдения в RAM. После рестарта теряет их; gateway сохраняет свои high-water marks до собственного рестарта. Одновременный рестарт не даёт долговечной защиты от replay. Подсказки не используются как fencing или основание изменения membership.
- Не добавляются actual-membership reports, автоматический join, scheduler, mTLS, дисковая персистентность и WAN-репликация.
- [Пустую storage-ноду нельзя возвращать под старым peer ID](REQUIREMENTS.md#r-019) в выжившую RAM-группу.

## Будущее направление, не текущая реализация

Управляемое добавление через oractl может назначать ноде шард, выдавать одноразовый bootstrap token, принимать созданный локально CSR и запускать learner/catch-up/membership-процедуру. Сертификат подтверждает идентичность, а не сам факт членства. Позднее scheduler сможет вызывать те же операции.

Для target подтверждены Raft, шарды, RF3, единый write-region и асинхронная межрегиональная репликация с outbox. Отдельные региональные группы, writer_epoch/fencing, позиции импорта и position-aware reads остаются деталями предложения. Допустимый lag, RPO/RTO, ACK и продление TTL при чтении в другом регионе остаются открытыми вопросами RFC-003/RFC-002. Это решение PoC их не закрывает.

## Приёмка

Проверяются: обновление лидера при неизменной config revision; задержанный меньший term; конфликт одинакового term; неизвестная нода/чужой регион/неназначенная реплика; отсутствие отката после пустого ответа CP; работа gateway при потере CP; реальная смена Raft-лидера с чтением ранее подтверждённых данных через прежний gateway. Корневой, CLI и generated модули проверяются отдельно.

- `internal/cpapi/leader_hints*_test.go` и `internal/gateway/leader_hints_test.go` проверяют контракт CP, term high-water marks и сохранение маршрутов.
- `internal/node/static_leader_cluster_test.go` использует реальные TCP gRPC и HTTP Raft, останавливает лидера, получает новую подсказку при той же revision и проверяет первый storage target после обновления. Затем блокирует CP и проверяет чтение подтверждённых данных и условную запись через прежний gateway.
- `internal/gateway/forwarder*_test.go` проверяют ограниченные повторы, запрет чужих адресов/регионов, вытеснение старых предпочтений новой подсказкой и сохранение успешного адреса при неизменной подсказке, включая завершение старого in-flight запроса после нового наблюдения.
- `/heartbeats` — read-only JSON со статической `config` и `leader_hints`, не каталог leases. `scripts/poc-smoke.sh` проверяет CLI и kill-leader failover изолированного Compose отдельно от Go-тестов.

Результаты конкретных запусков приведены в [отчёте](STATIC-LEADER-VERIFICATION.md); наличие тестов само по себе не означает, что Compose smoke выполнен.
